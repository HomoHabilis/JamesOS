# Development diagnostics and operational safeguards

`tools/build.py --diagnostics development` includes the private development commands, capture buffers and profiling code. `--diagnostics distribution` selects the public device configuration and rejects runtime profiling, panel and sector tests, and provisioning or namespace experiments. The pattern and project options selected by `--pattern-device-candidate` implement the shipped sequencer and save format.

Distribution excludes synthetic workloads and UI controls; private CPU, audio, USB, MIDI clock, worker, FX, register and power snapshots; per-job work ticks (0x9B) and same-half timing records; late and tail traces; the worker smoke job; foreground timing samples; the reporting-only startup RAM checksum; and the optional crash sidecar capture/read paths. The development build retains these facilities. A few configuration-dependent declarations may remain in source, but the build inspection checks the generated code and symbols, not just the command dispatcher.

Operational work is retained in both configurations:

- The audio load counters and the on-screen CPU meter. The audio interrupt keeps, for every half-buffer: the last and worst render time in timer ticks, overruns (a half longer than its deadline, 139,319 ticks at 44.1 kHz) since boot and since the last reset, halves rendered, late drops (0xB2) and an exponential average of the render time (64 halves). This costs a store, two compares, an increment and one shift-add per half in flash code, no RAM code. Three read-only commands answer at both build levels with the same replies: 0x60 (ten words: last, worst, overruns, halves, four USB-audio counters (zero in distribution builds, which do not keep them), average, overruns since boot), 0x61 `BR 01 00` (zeroes the since-reset counters; average and boot overruns stay) and 0xB2 (late drops, schema 3). None takes an address or length, none writes flash. With MONITOR on (TEMPO), the bottom two rows show the average load, a tick at the worst half since MONITOR was switched on, and turn red after an overrun; the MONITOR card shows AVG, MAX and OVR. The audio deadline, worker timeout, phase guard, mute and buffer ownership checks remain active.
- Flash busy-wait counters (`firmware/hal/fm1_flash.h`, kept in RAM since boot). Command 0xA1, no body, answers at both build levels with 24 bytes: `42 52 01 00` ("BR", schema 1), then five little-endian words: erases and page programs that finished after the normal bound (500 ms / 10 ms) but within the extended one (2 s / 50 ms), which are successful writes; the longest erase seen (µs); the longest page program seen (µs); software resets sent to the part (66h, 99h) because it was still busy at the extended bound (each one is a failed write, reported to its caller as an error); and the JEDEC ID as last read (at boot). It reads RAM only: no address, no length, no flash access. A part still busy 20 ms after such a reset makes the driver reset the CPU from RAM rather than switch execute-in-place back on, so that event is visible only as a reboot.
- Scheduler source-cost estimates and FX-job cost estimates remain because they determine the running audio schedule. MIDI clock timing and its fail-closed transport behavior remain.
- Startup still validates the worker, memory guards, watchdog, power transitions and prior boot state. The boot journal retains its header and boot identifier even when development timing samples are absent.
- The primary crash record and fault bundle, guarded reboot, rescue mode and loader remain. Distribution fault records mark development-only worker and FX detail as unavailable; this does not change their format. Diagnostic-only crash sidecars are reserved as empty address ranges to preserve the established retained-memory layout.
- Installer identity and transfer use the OTA protocol. Session status, guarded upload and restore, protection status and their buffers remain available; these are operational recovery paths, despite historical `diagnostic` names in their implementation.

`build-settings.json` records the selected configuration. The source and build checks do not by themselves qualify a release: installer, upgrade, recovery, saves and hardware behavior must be checked against the exact candidate package. See the project release tracker for current evidence and outstanding hardware coverage.

Build 2108 retains small physical-MIDI receive activity counters in the distribution image. They are not exposed by a distribution diagnostic command.
